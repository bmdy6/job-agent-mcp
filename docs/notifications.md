# 投递汇总与通知补发

日常和手动投递共用汇总格式：首行给出本轮状态及按平台的今日累计成功；平台行分别统计成功、不明、跳过、待续和失败。跳过、待续只列主要原因及数量，岗位明细仅保留成功、不明和失败。Telegram 发送一条消息，按 UTF-16 预算截去整条明细，并提示「其余 N 条见 dashboard」。完整结果仍在原有工作台与本地报告中。

今日累计按本地日期统计 `deliveries` 中取得成功回执的不同岗位；不明结果不计成功。旧 `daily-last-run.json` 缺少累计及续投时间时，只通过 `mode=ro` 连接读取同一天的数据库，并按当前配置估算可继续的最早时段；没有可用上下文时明确显示未记录，不把本轮数冒充当日数。新报告在发送前保存这两项元数据。续投时间表示策略允许的最早时间，实际执行由后续定时触发和平台状态决定。

`notify.send_one` 只对 `transport` 自动重试，最多总共 3 次，间隔 1、2 秒。单次 socket 等待不超过 10 秒，补发、重试和锁等待共用 50 秒截止时间。服务端明确的 API/HTTP 错误不自动重试；`notify_test` 始终只发一次，不读写补发队列。

待发消息保存在 `JOB_AGENT_HOME/notify-outbox.jsonl`，权限 0600。通知在发送前先写入文件，成功后逐条原子移除；transport 耗尽后保留，下次同一渠道发送时先按顺序补发。一次最多处理 10 条，同一渠道、标题、正文、链接均相同的待发消息不会重复入队。跨进程文件锁保护队列，文件损坏或无法保存时返回 `outbox_storage`，保留旧文件并在日志中提示，不报告发送成功。

队列只存消息与目标指纹，不存 Bot Token 或 Webhook 密钥。修改目标群、Webhook URL 或令牌后，旧目标的消息保留，不能自动转发给新目标；排查时需核对原目标和待发文件。全局或渠道未启用时不补发。

补发采用至少一次语义：若平台收到消息后连接中断，或者确认后进程在移除记录前退出，可能重复收到通知。outbox 只重发给用户本人的通知，不会重放招聘平台上的投递动作。旧版本已经丢失且未落盘的通知不会被自动恢复。
